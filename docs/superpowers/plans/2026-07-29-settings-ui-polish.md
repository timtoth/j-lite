# Settings UI Polish Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Collapse the App Info block into a single row with inline update status, replace all nine ad-hoc unicode icon glyphs with `lucide-react` equivalents, and fix accordion spacing, chevron shape, and header size in the Settings view.

**Architecture:** Pure renderer-side change. Adds one client dependency (`lucide-react`), edits six React components and one stylesheet, and bumps the app version. No server, IPC, or Electron main-process code is touched — `window.tc`'s update API and the `UpdateStatus` union are consumed exactly as they exist today.

**Tech Stack:** React 19, TypeScript 5.7 (strict), Vite 6, plain CSS (`client/src/App.css`), `lucide-react` 1.28.0.

Spec: `docs/superpowers/specs/2026-07-29-settings-ui-polish-design.md`

## Global Constraints

- **Worktree.** All work happens in `C:\GHSource\ticket-control\.claude\worktrees\feat+settings-ui-polish` on branch `feat/settings-ui-polish`. Never `cd` to `C:\GHSource\ticket-control`.
- **Verification command is `npm run build`** (from repo root). It runs `tsc -b` on the client and then `vite build`, so it is a real typecheck gate — it catches misspelled lucide imports and bad props. Baseline output: `✓ built in ~3s`, JS 412.13 kB, CSS 22.11 kB.
- **`npm test` (154 tests at baseline) must stay green.** It covers server/config/Electron-helper code only; nothing in it touches the renderer, so those 154 should be unaffected. Task 3 adds 8, ending at 162.
- **Client code is ESM.** `client/package.json` sets `"type": "module"`, so any new `.js` file under `client/` uses `import`/`export`, never `require`/`module.exports`. (The root package has no `"type"`, which is why `electron/*.impl.js` is CommonJS — don't copy that style into `client/`.)
- **`docs/` is gitignored** but specs and plans are tracked by convention. Use `git add -f` for files under `docs/`. Everything else adds normally.
- **Icon library is `lucide-react` version `^1.28.0`** — added to `client/package.json` (not the root `package.json`). React 19 satisfies its peer range.
- **Use `LoaderCircle`, not `Loader2`.** Verified against the installed package: `Loader2 === LoaderCircle` is `true` and both report `displayName: "LoaderCircle"`. `Loader2` is a deprecated alias. The spec names `Loader2`; this plan intentionally uses the canonical name.
- **All icons use `strokeWidth={2}` except chevrons, which use `strokeWidth={2.25}`.**
- **Never set an icon's color via a `color` prop.** Icons inherit `currentColor` so existing CSS `color`/`:hover` rules drive them. This is the actual fix for the two trash buttons.
- **Every icon inside a button that has no text needs `aria-hidden="true"`** — those buttons already carry `aria-label` or `title`, and the SVG must not add a second accessible name.
- **Commit after each task.** End commit messages with `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.

**On testing:** this repo has no renderer test harness (no jsdom, no React Testing Library, no component tests — `npm test` is `node --test` over server and Electron helpers). This plan does not add one; introducing a renderer test stack is a larger change than the feature and was explicitly out of scope in the spec. Consequently these tasks are verified by typecheck plus a scripted visual check, not by unit tests. Task 7 is the visual gate and is where regressions surface. Where a behavioral claim is cheaply assertable without a DOM (the `UpdateStatus` → icon/label/color mapping), Task 3 extracts it into a pure function and Task 4 tests it with `node --test`, matching the repo's existing test style.

### Task 3: Extract the update-status presentation into a pure module

The `UpdateStatus` → icon/label/color mapping is the one piece of real logic in this feature, and it is testable without a DOM. Pulling it out of the component means Task 4 can assert it with the repo's existing `node --test` setup, and `AppInfoCard` stays a thin renderer.

**Files:**
- Create: `client/src/components/settings/update-status-view.js`
- Create: `client/src/components/settings/update-status-view.d.ts`

**Interfaces:**
- Consumes: the `UpdateStatus` union from `client/src/global.d.ts`, which is exactly:
  ```ts
  export type UpdateStatus =
    | { state: "checking" }
    | { state: "up-to-date" }
    | { state: "downloading" }
    | { state: "ready"; action: "restart" }
    | { state: "ready"; action: "open-link"; version: string; url: string }
    | { state: "error"; message: string };
  ```
- Produces: `describeUpdateStatus(status)` → `null` when there is nothing to show, otherwise an object `{ icon, label, color, spin, title }` where `icon` is one of the strings `"check" | "x" | "arrow-up" | "loader"`, `label` is a string, `color` is a hex string, `spin` is a boolean, and `title` is a string or `undefined`. Task 5 imports this and maps `icon` to an actual lucide component.

The module is plain JS with a hand-written `.d.ts`, mirroring the existing `electron/*.impl.js` + `.ts` pattern in this repo — that is how this codebase already makes logic unit-testable under `node --test` without a transpile step. `node --test` cannot import `.tsx`, so the logic cannot live in the component file if it is to be tested.

**Use ESM syntax (`export` / `import`), not CommonJS.** This was verified empirically while writing the plan:

- `client/package.json` sets `"type": "module"`, so a `.js` file there is an ES module. A `require` call in it fails with `ReferenceError: require is not defined in ES module scope`.
- Bare `node --test` **does** discover `client/src/**/*.test.js`, so no test-script change is needed. Confirmed: the suite went from 154 to 156 with a two-test ESM probe.
- `tsc -b` typechecks a `.js` + `.d.ts` pair imported from a `.tsx` file, and **fails the build on a type error even in a file nothing imports** — verified by planting a deliberate `TS2322` and watching `npm run build` exit non-zero. So `npm run build` is a real gate on this module's types.

This differs from `electron/*.impl.js`, which is CommonJS because the root `package.json` has no `"type": "module"`. Do not copy that file's `module.exports` style here.

- [ ] **Step 3: Write the implementation**

Create `client/src/components/settings/update-status-view.js`:

```js
/**
 * Maps an UpdateStatus to the icon, label, and color the App Info row shows.
 * Returns null when there is nothing to display (no check has run yet).
 *
 * Kept as plain JS so `node --test` can exercise it without a transpile step.
 * `AppInfoCard.tsx` maps the returned `icon` string to a lucide component.
 */
export function describeUpdateStatus(status) {
  if (!status) return null;

  switch (status.state) {
    case "checking":
      return { icon: "loader", label: "Checking…", color: "#8888a0", spin: true, title: undefined };
    case "downloading":
      return { icon: "loader", label: "Downloading…", color: "#8888a0", spin: true, title: undefined };
    case "up-to-date":
      return { icon: "check", label: "Up to date", color: "#7ee2a0", spin: false, title: undefined };
    case "ready":
      return { icon: "arrow-up", label: "Update Available", color: "#e6c25a", spin: false, title: undefined };
    case "error":
      return { icon: "x", label: "Check failed", color: "#f5b7b1", spin: false, title: status.message };
    default:
      return null;
  }
}
```

There is no `module.exports` — the `export` keyword on the function is the whole export.
